WHERE WE STOPPED — 19 Aug 2026, evening
────────────────────────────────────────────────────────────────────────────
The test copy is NOT working on the server yet. Everything local is verified;
the open question is only where the files landed.

What is known good:
  · dist-test/ builds and was checked in a browser — its JS, chunks and fonts
    resolve under /calculator-test/, with no crossover to /calculator/.
  · Both .htaccess files pass `httpd -t`, and the gate was proven with a real
    Apache: anonymous 401, correct password 200, on every file in the folder.
  · The live pair (/print-calculator/ -> /calculator/print.html) is untouched
    and still works.

What happened:
  1. First attempt: the wrapper at /print-calculator-test/ DID render (dark red
     TEST BUILD bar), but the iframe showed the WordPress 404 page — meaning
     /calculator-test/print.html was not being served.
  2. After the next upload, /print-calculator-test/ itself returned Page Not
     Found too.

The useful inference: the site's WordPress .htaccess only rewrites paths that do
NOT exist (the standard !-f / !-d conditions). So a WordPress 404 means the file
is genuinely not at that path — this is a "where did the upload land" problem,
not a rewrite or permissions problem.

FIRST THING TO RUN TOMORROW

  for u in /print-calculator-test/ /print-calculator-test/index.html \
           /calculator-test/print.html /calculator-test/print.js \
           /print-calculator/ /calculator/print.html; do
    printf "%-38s %s\n" "$u" \
      "$(curl -s -o /dev/null -w '%{http_code}' -u x:x "https://clickclick.be$u")"
  done

  401 = there and gated (correct).  404 = not at that path.  500 = .htaccess
  rejected.  The last two lines are the control: they should be 401.

Then check in FileZilla that the server root has these as siblings of
calculator/ and print-calculator/:

  calculator-test/        .htaccess  print.html  print.js  customer.html
                          customer.js  chunks/  fonts/
  print-calculator-test/  .htaccess  index.html

Most likely cause: the upload landed one level deep, e.g.
/calculator-test/dist-test/print.html — which looks right in the client and
404s over HTTP. Second most likely: the hidden .htaccess files did not transfer
(FileZilla: Server > Force showing hidden files).

NOT a concern: the earlier warning that /calculator-test/print.html was publicly
exposed was over-stated. WordPress was intercepting the path, so the file was
never served. The .htaccess carries both RewriteEngine Off and the password
gate, so they arrive together — there is no window where it is reachable
without a password.
