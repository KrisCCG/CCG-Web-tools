## What changed today (in order)

### 1. Blank shop card after bot quote

**Symptom:** customer asks "A6 Biotop 300, 55 ex, recto/verso", bot replies with its intro text but no price card. Audit log shows:
```
{"event":"shop_quote","data":{"ok":false,"error":"delivery invalid"}}
```

**Cause:** Haiku 4.5 omits optional fields in tool calls. `delivery` was missing → `shop_validate()` rejected → `ok:false` → frontend `renderShopCard()` early-returned.

**Fix:** `smartbot-api/lib/shop.php` — `shop_validate(array &$in)` now takes the input array **by reference** and applies safe defaults instead of rejecting:

```php
if (!in_array($in['sides']    ?? '', SHOP_SIDES,    true))
    $in['sides']    = ($in['product'] === 'card') ? 'double' : 'single';
if (!in_array($in['delivery'] ?? '', SHOP_DELIVERY, true))
    $in['delivery'] = 'pickup';
if (!isset($in['express']) || !is_bool($in['express']))
    $in['express']  = !empty($in['express']);
```

Catalog correctness checks (product / size / paper_key / qty) still hard-fail — those aren't bot-laziness defaults.

### 2. Shop card rendered in English during a French conversation

**Symptom:** bot speaks French, page chrome is French, shop card shows "ONLINE SHOP REFERENCE PRICE" / "incl. VAT" / "ORDER ONLINE" in English.

**Cause:** bot passes `lang: "fr"` in its tool input (per the tool schema), but `shop.php` only used it for the deep-link URL — it never echoed `lang` back in the response dict. The frontend then fell through to `state.lang`, which could be `'en'` if the customer clicked the FR button **after** the card was rendered (the card doesn't auto re-translate).

**Fix (two parts):**

`smartbot-api/lib/shop.php` — add `lang` to the response:
```php
'lang' => in_array($in['lang'] ?? '', ['fr','nl','en'], true) ? $in['lang'] : null,
```

`smartbot/index.html` `renderShopCard()` — pick the card's language from the tool-call value first, with defensive fallbacks:
```js
const cardLang = quote.lang || conversationLang();
const tShop = (key) =>
  ((window.I18N[cardLang] || {})[key])
  || ((window.I18N.en || {})[key])
  || key;
```
All five `tChat('shop_*')` calls inside the card became `tShop('shop_*')`.

### 3. Timeout handling + payload-size logging

**Goal:** stop a stuck Anthropic call from manifesting as a blank PHP page; gain visibility on context bloat.

**Changes:** `smartbot-api/lib/anthropic.php`
- New constants: `ANTHROPIC_TIMEOUT_S = 25`, `ANTHROPIC_CONNECT_TIMEOUT_S = 5`.
- `curl_errno()` captured. On `CURLE_OPERATION_TIMEDOUT` (28) the wrapper throws `RuntimeException("[anthropic_timeout] …")` — a tagged prefix the chat/start endpoints can detect.
- New `audit_log('anthropic_request', …)` written before every call, with `bytes`, `msg_count`, `tool_results` (count of accumulated tool_result blocks), and `model`.

**Catch-block update:** `chat.php` + `start.php`
```php
$is_timeout = str_starts_with($e->getMessage(), '[anthropic_timeout]');
http_response_code($is_timeout ? 504 : 502);
echo json_encode(['ok' => false, 'error' => $is_timeout
    ? 'The assistant is taking longer than usual — please try again in a moment.'
    : 'Assistant temporarily unavailable.']);
```

**Outside-of-code:** Infomaniak Manager → Hosting → PHP & MySQL → PHP version & options → `max_execution_time = 60`. With cURL capped at 25s, this leaves 35s headroom for the rest of the request before PHP itself would kill the process.

**Watching for bloat:** tail the audit log and watch the `bytes` field of `anthropic_request` events grow over a single conversation. Realistic intake should stay well under 100kB. Anthropic's hard cap is ~200k tokens (~800kB JSON, rough).

### 4. Asking about two products crashed the second request

**Symptom:** "I want flyers and posters, single sided" → bot replies with one flyer card, customer says "and the posters?" → "Assistant temporarily unavailable."

**Cause:** when the customer asks about multiple products at once, Haiku emits **two** `check_shop_pricing` tool_use blocks in a single response. The old code did:
```php
$shop_call = extract_tool_call($response, 'check_shop_pricing');  // first one only
```
So only the flyer got executed, only one `tool_result` got appended. On the next turn Anthropic saw an orphaned second `tool_use` with no matching `tool_result` → HTTP 400.

**Fix:** `chat.php` + `start.php` — replace the single-call extractor with a loop over **every** `tool_use` block in the response. Bundle all `tool_result` blocks into one user-role message (Anthropic's required shape):

```php
$shop_quotes  = [];
$submit_call  = null;
$tool_results = [];

foreach ($response['content'] ?? [] as $block) {
    if (($block['type'] ?? '') !== 'tool_use') continue;
    $tu_id = $block['id'] ?? '';  $tu_name = $block['name'] ?? '';  $tu_in = $block['input'] ?? [];

    if ($tu_name === 'check_shop_pricing') {
        $quote = shop_get_quote($tu_in);
        $shop_quotes[]  = $quote;
        $tool_results[] = ['type' => 'tool_result', 'tool_use_id' => $tu_id,
                           'content' => json_encode($quote, JSON_UNESCAPED_UNICODE)];
    } elseif ($tu_name === 'submit_request') {
        $submit_call = ['id' => $tu_id, 'input' => $tu_in];
    }
}
if (!empty($tool_results)) $updated_history[] = signed_turn('user', $tool_results);
```

Response JSON now returns:
- `shop_quotes` — array (new, primary)
- `shop_quote` — first element (kept for back-compat)

`smartbot/index.html` — render one card per quote:
```js
const quotes = (data.shop_quotes && data.shop_quotes.length)
               ? data.shop_quotes
               : (data.shop_quote ? [data.shop_quote] : []);
if (quotes.length) {
    state.lastShopQuote = quotes[quotes.length - 1];
    quotes.forEach(renderShopCard);
}
```

### 5. Express button not activated on shop after bot quoted express

**Symptom:** customer asks for "urgent" / "express", bot quotes a price, customer clicks ORDER ONLINE, shop opens with the Express checkbox unchecked and the price reflects no express premium.

**Two compounding causes:**

**(a) Bot omits `express: true` in the tool call.** Same Haiku-omits-optionals pattern as `delivery`. The old system prompt only said *"express: false unless customer said urgent/rush"* — too terse.

Fix: `smartbot-api/system_prompt.php` — explicit multilingual triggers + "never omit" instruction:
```
- express:  Set TRUE whenever the customer signals urgency. Triggers
            include: "express", "urgent", "rush", "asap", "as soon as
            possible", "vite", "rapide", "pressé", "urgent", "express"
            (FR), "snel", "vlug", "spoed", "urgent", "express" (NL),
            or a deadline of "tomorrow / demain / morgen" or "within 48h".
            Otherwise false. ALWAYS include this field — never omit it.
- delivery: "pickup" unless customer asked for delivery. ALWAYS include
            this field — never omit it.
```

**(b) Shop sets `expressChk.checked = true` silently, without dispatching a `change` event** — so `applyExpressDeliveryLock()` (DPD label disable) and `invalidatePrice()` (price refresh) didn't fire on prefill.

Fix: `Clickclick-flyer-calculator/flyers/index.html` `applyUrlPrefill()`:
```js
const expressChk = document.getElementById('expressChk');
if (expressChk && state.express) {
  expressChk.checked = true;
  expressChk.dispatchEvent(new Event('change', { bubbles: true }));
}
```

**Note:** with (a) fixed, the bot's quoted price already reflects express automatically — `shop_get_quote` sends `express=1` to `calc.php`, which returns the +35% price. No separate UI work needed for the bot card's price; it just inherits.

**Diagnostic if it ever recurs:** right-click ORDER ONLINE → Copy Link. If the URL has `&express=1` → it's a shop prefill bug. If `&express=0` → the bot didn't capture express intent.

### 6. Reordered the configurator: artwork now step 4, details now step 5

**Why:** the old flow asked for customer details (step 4) **before** the customer had even added their first item to the cart (step 5 was upload + "Add to order"). The natural cart-style flow is: configure → upload art for *this* item → add → repeat → fill details once at the end → place order.

**Fix:** `Clickclick-flyer-calculator/flyers/index.html` — swap the two `<div class="step">` blocks. Renumber the visible `<span class="num">` badges (artwork = 4, details = 5). i18n keys kept their original semantic mapping (`step4.*` still means "Your details", `step5.*` still means "Upload your artwork") — purely a key-name cosmetic, no user-visible effect.

The right-side sticky cart and final `.btn-order` ("Place order") live in `<aside>` and are unaffected.

### 7. Price on the "Add to order" button always readable

**Symptom:** when the button is disabled (no artwork uploaded yet), the entire button — including the €X,XX amount — went grey at 13px. The price is the most important info on the artwork step.

**Fix:** `Clickclick-flyer-calculator/flyers/index.html` CSS — `.btn-add .amt` always renders prominently regardless of the button's disabled state:
```css

                         text-transform:none; opacity:1 }
.btn-add:disabled .amt { color:var(--ink); font-size:22px; opacity:1 }
```

### 8. Sticky price banner above "Your order"

**Goal:** make the live item price the most prominent number on the page, always in view while the customer is configuring (even before they upload artwork).

**Fix:** `Clickclick-flyer-calculator/flyers/index.html` — new `.item-price` banner inserted as the first child of `<div class="price-card">`, before the `<h3>Your order</h3>`. Because `.price-card` is `position: sticky; top: 92px`, the banner stays in view while the customer scrolls through steps 1–5.

Visual: indigo bleed-to-edge band (negative margins to negate the card's `padding: 28px`), small uppercase label above, 34px (28px mobile) bold price, "incl. VAT" caption below. Shows "—" before a price is computed.

Wired into the existing `updateAddButton()` so it refreshes whenever `state.draft.price` changes:
```js
const priceAmt = document.getElementById('itemPriceAmt');
if (priceAmt) priceAmt.textContent =
    state.draft.price ? fmtMoney(state.draft.price.inclVat) : '—';
```

i18n keys added in EN/FR/NL: `itemPrice.label`, `itemPrice.sub`.

## Haiku 4.5 gotchas (recurring pattern)

The recurring root cause across today's bugs was the same: **Haiku 4.5 silently omits optional tool parameters**, even when the schema description says to include them. Defensive coding:

1. **Server-side safe defaults** for any optional field the bot might skip. Coerce/normalise instead of rejecting. (See `shop_validate()` mutating `$in` by reference.)
2. **Explicit "ALWAYS include this field — never omit it"** instructions in the system prompt for any field that matters.
3. **Multilingual trigger examples** in the prompt for fields whose values depend on customer intent (e.g. express).
4. **Echo critical inputs back to the frontend** so UI doesn't have to guess the bot's state. (See `lang` in `shop_get_quote()` response.)

Sonnet 4.5 was more compliant but slower and rate-limited at our budget. Haiku 4.5 stays — we just code around its terseness.
