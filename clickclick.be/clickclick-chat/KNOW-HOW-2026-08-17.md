## Decisions taken today

### 1. tiegel.be is scaffolding, not a brand

Confirmed by Kris: it is a cheap URL bought to build the new site on, with **no relation to
the company**. The new site's real destination is **clickclickgraphics.com**, which it
replaces — the old thin 2019 site retires rather than being rescued.

Consequences:

- **Never point anything permanent at tiegel.be** — no QR codes, no print, no ads, no links
  from the old site. All become dead links on migration day.
- Anything that must outlive the staging domain moves to clickclick.be now. That is what
  the rest of this document is about.
- The shop stays at `clickclick.be/flyers/` **permanently**. It is the one URL safe to print
  today, because the marketing site is the thing that moves, not the shop.

### 2. The request bot is retired; smartbot becomes production

`/request/` was the first attempt. `/smartbot/` supersedes it because it promotes the shop —
it quotes standard products instantly via `calc.php` and hands off to `/flyers/` with
prefilled URL params.

### 3. "Smartbot" was an internal codename — the product is called **Chat**

Renamed everywhere, including customer-visible strings.

### SPF — the email advice was backwards. Corrected.

`secrets.example.php` claimed the `From:` domain must match the host the bot runs on. **That
is not how SPF works,** and following it would have broken mail. `submit.php` aligns
envelope-from to `from_email` via `-f`, so SPF is evaluated against **the domain in that
address** and Infomaniak's outbound IP. Where the PHP files sit is irrelevant.

Actual records, checked 17 Aug 2026:

| Domain | SPF | Can send? |
|---|---|---|
| clickclickgraphics.com | `v=spf1 include:spf.infomaniak.ch ~all` | **yes** |
| clickclick.be | `v=spf1 -all` | no — declares "sends no mail" |
| tiegel.be | `v=spf1 -all` | no |

The live `secrets.php` already uses `noreply@clickclickgraphics.com` and always has — mail
has been fine all along, and the move does not affect it. Had the example file been followed
and `from_email` set to `noreply@clickclick.be`, every notification would have hard-failed
SPF and been rejected.

`clickclick.be` publishing `-all` is correct hygiene for a domain that never sends mail —
leave it. Just never send **from** it. The example file now records all three records inline
so this can't be got wrong again.

### 3. Bot was telling customers we don't deliver

**Symptom (spotted live):** *"our online shop handles pickup … For delivery, you'd need to
arrange that with the team … Shall I show you the pickup price first?"*

**Cause:** the system prompt mentioned `delivery` only as a tool-parameter default
(`"pickup" unless customer asked`). Nothing told the model delivery was *purchasable*, so it
filled the gap by inventing a team hand-off.

**Fix:** new `DELIVERY — WE DO DELIVER` block in `chat-api/system_prompt.php`, stating the
flat fee, forbidding the team hand-off and the "pickup price first" split, and forbidding
arrival dates.

**Verified against the live endpoint:** 500 A5 flyers, ms130, double-sided —
pickup `inclVat: 102`, dpd `inclVat: 117`. Exactly EUR 15, added once per order.

**Two things found while fixing it:**

- `calc.php` returns **no** `readyDate` / `readyDays` — the flyers frontend computes them.
  `shop.php` reads both with `?? ''` / `?? 0` fallbacks, so the bot always receives empty
  values. Harmless, but the bot can never quote a lead time from the shop. Documented in the
  `shop.php` header; the prompt now forbids arrival dates outright.
- **The EUR 15 is a flat fee, not a minimum** — accepted as-is for now (Kris, 17 Aug).

### 4. The shop was promising a delivery date it cannot meet

**Found while fixing the above.** With DPD selected, the shop labelled its date
`ready.ship` = "Ready for delivery on" / *"Livraison le"* / *"Levering op"*. All three read as
an **arrival** promise — but the date is production-completion only
(`PRODUCTS[].days` = 5 working days, or 2 for express). DPD transit is not in the calculation
at all. In Belgium a stated delivery date creates obligations, so this mattered.

**Fixed** in `flyers/lib/i18n.js`, all three languages:

| | was | now |
|---|---|---|
| EN | Ready for delivery on | **Ready to ship on** |
| FR | Livraison le | **Prêt à expédier le** |
| NL | Levering op | **Klaar voor verzending op** |

**Belgium-only pushed** into `deliver.shipSub` in all three languages
("DPD Home — Belgium only · or by bike in Brussels", etc.).

**Also found: express and DPD are mutually exclusive.** `flyers/index.html:1144` forces
`delivery = 'pickup'` when express is switched on, and the DPD label is disabled — DPD can't
make 48 h. The bot didn't know this and could have quoted a combination the customer was
unable to order. Now stated in the prompt.

**Lead-time policy given by Kris and written into the prompt:** standard production 5 working
days ("within a week"), express 48 h, both production-only; DPD transit on top is not in our
hands; the customer gets a tracking code when it ships. The bot must never give an arrival
date.

### 5. Country field + out-of-Belgium quote flow (NEW — needs browser testing)

**Ready-date maths verified first.** The shop's algorithm (`flyers/index.html`) steps forward
one calendar day at a time and counts only Mon–Fri until it reaches 5. Confirmed correct:
order Mon 17 Aug → ready Mon 24 Aug; order Thu 20 → Thu 27; order Sat/Sun → Fri 28.

**All four caveats below are now FIXED — see section 6.**

Four caveats found:
1. **Belgian public holidays are not excluded** — only Sat/Sun. An order on Mon 21 Dec counts
   Christmas Day as a working day and promises Mon 28 Dec.
2. **No cut-off time.** An order at 23:50 counts the next day as day 1, same as one at 09:00.
3. **Computed in the customer's browser**, from their clock and timezone.
4. **Never stored.** The promised date is display-only — not sent to `pay.php`, not in the
   order JSON, not on the invoice. Nobody on our side can see what a customer was told.

**Built:**
- `calculator/quote.php` (new) — validates, writes `orders/quotes/<id>.json`, emails shop@
  with Reply-To set to the customer. Rate-limited 10/IP/h, CSRF-checked, mirrors `pay.php`.
  Quotes no price on purpose: unpriceable shipping is the whole reason it exists. Protected
  by the existing `orders/.htaccess` (`Require all denied` cascades to subdirectories).
- `flyers/index.html` — country `<select>` (BE default, NL/FR/DE/LU/Other), DPD disabled for
  any non-BE country, Pay button swapped for a "Request a quote" panel.
- `flyers/lib/i18n.js` — 13 new keys × 3 languages.

**Collision caught during the build:** the new panel keys were named `quote.*`, but
`quote.title` already exists ("Your quote" / *"Votre devis"* / *"Je offerte"*). Duplicate keys
in the same object literal mean the later definition wins, so the panel would silently have
shown the wrong heading. All new keys moved to an `intl.*` namespace. A script now checks
every key used in `index.html` resolves in `i18n.js` — all do.

**Still not enforced beyond the dropdown:** the checkout has no free-text country field (`custAddress/City/Zip`,
`shipAddress/City/Zip` only). The labels now *say* Belgium only and the bot routes foreign

### 6. Production deadline: recorded on the order and on the shop@ mail

Asked for by Kris: the last possible production deadline must be visible internally.

### 7. "Card on Biotop 250" arrived in the shop as MultiArt Silk 130

**Reported by Kris after testing the live chat.**

**Root cause — a catalog mismatch between three layers:**

| Layer | Knows |
|---|---|
| `calc.php` | any paper for any product — it priced a **flyer on Biotop 250** at €56 |

**Fixed in three places:**

1. `chat-api/lib/shop.php` — new `SHOP_PAPER_BY_PRODUCT` mirroring the shop's real per-product

2. `flyers/index.html` — a deep-linked paper that doesn't exist for the product no longer

3. `chat/index.html` — **no more bare-shop fallback.** No deep link → no Order button, rather

Plus `system_prompt.php`: how to phrase the new error, and an explicit rule that the product
must match what the customer said (card ≠ flyer).

**Left alone deliberately:** `calc.php` still prices any paper for any product. Tightening it

⚠ **`SHOP_PAPER_BY_PRODUCT` now duplicates the shop's paper lists in a second repo.** If the

### 8. Bot interrogated instead of quoting

**Symptom:** *"are these business cards (85×55) or a different card format? And single- or
double-sided?"* — asked before showing any price.

**Cause:** the prompt listed the tool trigger as `product + size + paper + qty`, and had a
default for `sides` but none for `size`. So a missing size blocked the quote and the model
asked for it.

**Prices are NOT the same across card sizes** (Kris assumed they were; checked live,
bt250 @ 100):

| | single | double |
|---|---|---|
| BC | 53 | 54 |
| A7 | 53 | 56 |
| A6 | 56 | 59 |
| A5 | 61 | 66 |
| A4 | 72 | 81 |

A4 double is ~53 % above BC single, so the bot genuinely cannot guess silently.

**Fix — assume and disclose, rather than ask or hide.** Added a `size` default (BC / A6 / A3
per product), dropped size and sides from the trigger (now `product + paper + qty`), and added
a NEVER INTERROGATE rule: quote immediately, then state the assumption in one line
("standard business cards, 85×55, double-sided — say if you meant another size"). Customer
gets a price instantly and can correct it, and we never quote a size we didn't name.

### 9. A 401 does not prove basic-auth is configured correctly

Testing the cron endpoint with real credentials returned **HTTP 500**, not the expected output.

**Cause:** `chat-api/.htaccess` pointed `AuthUserFile` at
`sites/clickclick.be/chat-api/.htpasswd` — a file that was never uploaded (it isn't in the
repo, and `**/.htpasswd` is in the SFTP ignore list).

**The lesson, which cost a false "verified" earlier in the day:** Apache sends the 401
challenge from the `AuthType` directive alone. It only opens `AuthUserFile` when validating a
password that was actually submitted. So:

- anonymous request → 401 means *the directive parsed*, nothing more
- wrong/missing `AuthUserFile` → **500, only after credentials are supplied**

An unauthenticated `curl` can therefore never confirm a basic-auth gate works. **Always test
with `curl -u USER <url>` and enter the password.**

**Fix:** point at the shared `sites/clickclick.be/flyers/.htpasswd`, matching what
`calculator/.htaccess` and `calculator/admin/.htaccess` already do — one credential for the
estate, no password file needed in `chat-api/` at all. The commented-out gate in
`chat/.htaccess` was corrected the same way (it still had `REPLACE_WITH_INFOMANIAK_UUID`).

Only `print-calculator/.htaccess` still uses its own `.htpasswd`; that one predates this and
works, so it was left alone.

## 11. Cron runs now leave a record (added 18 Aug 2026)

`cleanup.php` and `retention.php` only ever echoed to stdout. The Task Scheduler captures
that, but nobody can inspect it afterwards — so "did the 05:00 job actually run?" was
unanswerable without digging through the server access log.

**New `chat-api/lib/cronlog.php`:**

- `cron_log()` appends one line per run to `chat-api/logs/cron.log` — timestamp, script,
  duration and all counts. Trimmed in place at 500 lines, so it cannot grow unbounded.
- `cron_log_tail()` echoes the last 5 runs, so an authenticated
  `curl -u USER https://clickclick.be/chat-api/cleanup.php` shows recent history directly.
  `logs/` is `Require all denied` over HTTP by design, so this is the only outside view.

Both scripts call both. `logs/` is already git-ignored, so `cron.log` never reaches the repo.

**Bug caught in the dry run, worth remembering:** the helper first used `__DIR__ . '/logs'`,
but it lives in `lib/` — so `__DIR__` is `chat-api/lib`, and the log was written to
`chat-api/lib/logs/cron.log`. Wrong directory, and outside the folder `cleanup.php` prunes.
Now `dirname(__DIR__)`. **In a shared include, `__DIR__` is the include's own directory, not
the caller's.**

**Schedule reminder:** `cleanup.php` is daily (`0 5 * * *`), `retention.php` is Sundays only
(`0 5 * * 0`) — so on a weekday, only cleanup should appear in the log.

## Mail routing — decided today

Rule set by Kris: **nothing from the shop goes to a personal address**, because colleagues
need access to it too.

| Traffic | Goes to |
|---|---|
| Quote requests (chat bot) | `info@clickclickgraphics.com` — unchanged |
| Shop orders (calculator) | `shop@clickclickgraphics.com` |
| Sender identity, bot | `noreply@clickclickgraphics.com` — a real Infomaniak mailbox, never read |
| Sender identity, shop | `shop@clickclickgraphics.com` |

`noreply@` exists as a real mailbox on the hosting account, which is what Infomaniak requires

  a mail recipient. Changing it breaks the nightly encrypted backup.
- `calculator/BACKUP.md:54,70` — `kris@clickclick.be` is an **SSH username**, not an email.

**Decided — internal ops alerts stay off the shop address.** `alert_email` (backup failures),

The shop-address rule therefore applies to **customer-facing shop mail only**, not to
